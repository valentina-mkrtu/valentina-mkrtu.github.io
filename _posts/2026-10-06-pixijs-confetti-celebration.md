This recipe includes observations from a small synthetic PixiJS browser fixture. The fixture configures a native NixieFX effect in code; it does not claim to verify an editor-exported bundle.

Confetti works best when it marks a specific accomplishment. If it appears every time a results panel rerenders, the celebration can become visual noise and a source of unnecessary allocations. The effect therefore needs more than attractive colors. It needs a trigger that belongs to the achievement, a finite lifetime, and a cleanup path that belongs to the screen.

This recipe uses a fictional level-completion panel. The player receives one celebration for a confirmed completion event. Reopening the panel or receiving the same event again should not produce another burst during that scene's lifetime.

## Define the celebration before choosing particles

The example has four requirements. The score and reward text appear immediately. A new completion identifier may start one burst. Repeated identifiers do not replay it. When reduced motion is enabled, the panel still communicates success without decorative movement.

Use a separate effect layer behind the result text. Choose its bounds from the panel layout, including safe areas and smaller viewports. Particles should not cover the primary action or make the next step difficult to find. Begin with one short burst and add visual complexity only after that basic behavior is correct.

## Author a deliberately small first version

For a first design, use flat confetti pieces, a finite burst, varied initial rotation, and a downward fall. A proposed starting budget is 32 pieces with a maximum authored lifetime of 1.2 seconds. These are design inputs, not a performance claim or a measurement of a completed demo.

The [NixieFX PixiJS guide](https://nixiefx.com/pixijs-particle-effects/) provides an integration path for teams looking for a pixi js particle editor. Export the authored effect and inspect it in the intended PixiJS scene before treating the editor preview as the final appearance.

For this recipe, avoid lit shading and mesh-surface emission, which PixiJS does not support. Do not depend on editor preview bloom surviving export. The celebration should remain readable with simple flat particles and the scene's actual background.

## Deduplicate the game event

The following helper is ordinary application code. It remembers completion identifiers for one results scene and calls an injected function that starts the exported effect. It is not a NixieFX API wrapper.

```js
export function makeCelebrationGate(play) {
  const seen = new Set();
  let closed = false;
  return {
    accept(eventId, reducedMotion = false) {
      if (closed || typeof eventId !== "string" || !eventId || seen.has(eventId)) {
        return false;
      }
      seen.add(eventId);
      if (reducedMotion) return false;
      play(eventId);
      return true;
    },
    dispose() {
      closed = true;
      seen.clear();
    }
  };
}
```

Construct the gate when the scene is created and dispose it when that scene is destroyed. Use a stable completion identifier from the application's confirmed event, not a fresh timestamp generated by the UI. Otherwise each rerender can look like a new accomplishment.

The injected play function should enforce a maximum of one active decorative effect. If another distinct completion arrives during the burst, keep its factual reward update and skip its extra confetti. That is this example's overlap policy; a game with queued achievements may choose a different policy explicitly.

## Connect the exported effect to its owner

Prepare the effect in the editor, validate it, and export its runtime bundle. In the PixiJS host, load the manifest, the referenced compiled effect, and the assets required by that export. Record the installed package versions rather than assuming an integration snippet from another version is compatible.

Create the effect renderer under the celebration layer. The play function should place one instance at the panel's intended burst origin and retain its handle. Advance the renderer exactly once per host frame using seconds. When the instance finishes, remove it from the renderer and clear the retained handle.

On scene exit, stop accepting completion events, dispose the gate, detach the ticker callback, and destroy the renderer. Remove any event subscription associated with the scene. If textures are shared with another view, release them through the project's existing ownership mechanism instead of destroying them indiscriminately.

## Work through a concrete event sequence

Use synthetic identifiers to make the expected result easy to inspect. Deliver completion A twice: the score updates correctly and only the first event may start confetti. Reopen the panel without recreating the scene: the same identifier should remain suppressed. Deliver completion B while a burst is active: the reward information changes, but the overlap policy skips another decorative instance.

Next, create a fresh scene with reduced motion enabled. Completion C should update the visible success message and reward information without launching confetti. If the preference changes while particles are visible, remove that decoration immediately. Finally, exit during a burst and confirm that the old scene cannot receive another completion event.

In one Chrome/macOS development run with PixiJS 8.22.0 and NixieFX 0.1.17, six checks passed: initial completion, duplicate suppression, overlap suppression, inactivity after 1.5 simulated seconds, reduced-motion suppression, and clearing the owned effect handle. At 0.15 seconds, the 880 × 260 canvas showed 32 visible particles in two render groups, with no missing-texture or unsupported-feature diagnostics. These are functional observations, not a performance benchmark or a heap-leak audit.

## Review the effect as part of the interface

Capture a real frame that shows both the particles and the readable result text. Record the viewport, seed, export revision, and simulation time so another person can reproduce the composition. Check a small viewport and the reduced-motion path as separate cases.


## Reproduce the native effect settings

For a texture-free test, import `createDefaultParticleEffect` and `createConstantParticleScalar` from `nixie-fx`, and `PixiVfxRenderer` with `createPixiVfx2dProjection` from `nixie-fx/pixi`. The fixture used two copies of this emitter, each with a different ID and color:

```js
const effect = createDefaultParticleEffect();
effect.timeline.duration = 1.4;
effect.timeline.loop.enabled = false;
const e = effect.emitters[0];
e.loop = false;
e.duration = 0.1;
e.maxParticles = 24;
e.spawn.rate = 0;
e.spawn.rateValue = createConstantParticleScalar(0);
e.spawn.bursts = [{time: 0, count: 16, cycles: 1,
  interval: 0, probability: 1}];
e.spawn.shape = "box";
e.spawn.box = [29, 0.15, 0];
e.spawn.position = [0, -3, 0];
e.initializeParticle.lifetime = createConstantParticleScalar(1.2);
e.initializeParticle.size = createConstantParticleScalar(0.35);
e.initializeParticle.velocity.mode = "vector";
e.initializeParticle.velocity.min = [-2, 1, 0];
e.initializeParticle.velocity.max = [2, 4, 0];
e.billboard.shape = "square";
e.billboard.sizeValue = createConstantParticleScalar(1);
e.billboard.softness = 0;
```

Use a downward-positive projection with 20 pixels per unit and origin `(440, 130)` for that canvas. Create an instance with seed 42 and advance in seconds; the inspected frame used nine steps of `1 / 60`. Two 16-piece emitters produce the 32-piece budget. This setup uses constant downward velocity; gravity, varied rotation, responsive layout, and reacting to a mid-burst preference change remain integration work rather than tested claims.
